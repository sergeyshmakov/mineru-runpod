There are three ways to get a mineru-runpod endpoint running. Pick the one that matches what you need to control.

## Option A — Deploy from the RunPod Hub (easiest)

**[Deploy this endpoint from the RunPod Hub →](https://console.runpod.io/hub/sergeyshmakov/mineru-runpod)**

New to RunPod? [Create your account first](https://runpod.io?ref=31jdfpnq), then come back and click Deploy.

This repo is published as a public Hub template. Open the listing above and click Deploy — or, from the RunPod dashboard, go to **The Hub → Serverless repos**, find `mineru-runpod`, and click Deploy. RunPod builds the image on your account, you pick a GPU pool, and you get an endpoint id. No fork, no clone, no local setup.

The template is the *source*, not a prebuilt image: there is no public image
to pull, and RunPod builds one into your own account's registry the first
time you deploy (~5–10 min, watchable in the dashboard). That also means
your local machine's architecture is irrelevant — nothing is built on it. If
you create an endpoint by hand and type an image name instead, the pull
fails with an access error; see
[troubleshooting](/guides/troubleshooting/#you-dont-have-access-to-download-the-artifacts).

This is the recommended path if your goal is parsing documents, not customising the worker.

## Option B — Fork and auto-build (for customization)

Fork this repo into your own GitHub account if you want to:

- Pin different versions of MinerU, vLLM, or other dependencies
- Modify `handler.py` (custom input validation, extra output formats, etc.)
- Run on a private GitHub repo

Then in the RunPod dashboard:

1. **The Hub → Serverless repos → Import Git Repository**, point at your fork. Branch `main`, Dockerfile path `Dockerfile`.
2. RunPod builds the image (~5–10 min, watchable in the dashboard) and gives you a `template_id`.
3. Create the endpoint. Pick one:
   - **(B1) Dashboard, no local Python needed:** **Resources → Serverless → New Endpoint**, select your template, set `idle_timeout=10`, `workers_min=0`, `workers_max=3`, FlashBoot on, GPU pool `ADA_24` (RTX 4090). Save and grab the endpoint id.
   - **(B2) As code, reproducible across deployments:**
     ```powershell
     cp .env.example .env       # fill RUNPOD_API_KEY and MINERU_TEMPLATE_ID
     pip install -e .[deploy]
     python deploy.py --template-id $env:MINERU_TEMPLATE_ID
     ```
     Every knob in `deploy.py --help` matches a setting in the dashboard.

Subsequent pushes to `main` on your fork rebuild the image automatically; the endpoint picks up the new image on next cold start (or force a redeploy from the dashboard).

## Option C — Bring your own image

For full control over the Docker layer, build and push to Docker Hub or GHCR yourself, then:

```powershell
python deploy.py --image yourhandle/mineru-runpod:0.1
```

This skips RunPod's auto-build entirely. Use it when you need custom base images, multi-stage builds, or air-gapped registries.

## Endpoint defaults

| Setting | Value | Why |
|---|---|---|
| `gpu_ids` | `ADA_24` | 24 GB Ada / RTX 4090, the default since 1.x, where it measured cheaper per page than the A5000 (`AMPERE_24`). MinerU 4 sizes vLLM to about 6 GB of the card for the [`MinerU2.5-Pro-2605-1.2B` VLM](https://huggingface.co/opendatalab/MinerU2.5-Pro-2605-1.2B). |
| `idle_timeout` | `10 s` | Scale workers to zero after 10 s of inactivity |
| `workers_min` | `0` | Pay only when processing |
| `workers_max` | `3` | [Concurrency](/guides/concurrency/) cap (parallel workers); bump for production |
| `execution_timeout` | `900 s` | Per-job cap; size it to your longest document. `deploy.py` applies it for you with a `PATCH` to the REST API, because the SDK's `create_endpoint` still has no parameter for it. If that call fails the summary line reads `execution timeout: NOT SET (…)` and names the reason — set it in the console when you see that, since the endpoint is otherwise on RunPod's own default rather than this one. |
| `flashboot` | `true` | RunPod's fast cold-start tech |

## Host and image

The image is built on vLLM's CUDA 12.9 build, so a worker host needs a CUDA
12.9 or newer driver. The Hub listing limits the endpoint to CUDA 12.9 and 13.0
hosts for you. `deploy.py` sets no such filter: on an endpoint you create with
it or by hand, set the allowed CUDA versions to 12.9 and 13.0 in the endpoint
settings, or a worker can land on an older host and fail to start.

The GPU pools are the same as in 1.x: `ADA_24` (the default), `AMPERE_24` and
`AMPERE_48`. Blackwell cards (RTX 5090, RTX PRO 6000, B200) are being verified
for 2.x; until then the Hub listing does not offer them.

The model weights are baked into the image, under MinerU's own model root: the
VLM (2.3 GB) and MinerU 4's small-model bundle (0.9 GB), about 3.2 GB where 1.x
carried about 17.5 GB. Nothing is downloaded at runtime, so no network volume or
RunPod Cached Models entry is needed. The 50 GB default container disk holds the
image plus the working room a parse needs; check it with `df -h` on a real
worker before parsing books that produce multi-GB archives.

## Environment variables

Every setting on the Hub form is optional, and an endpoint runs with all of them
at their defaults. Three are new in 2.x and worth a look before the first
deploy:

| Variable | Default | What it does |
|---|---|---|
| `MINERU_WARMUP_TIER` | `standard` | The tier the boot warmup parses with, so its models are loaded before the first job. Set it to the tier most callers use; `flash` and `basic` never load the VLM. |
| `MINERU_VIRTUAL_VRAM_SIZE` | detected VRAM | The VRAM, in GB, MinerU sizes itself for. MinerU 4 gives vLLM about 6 GB of any card; a smaller value gives it a bigger share (12 on a 24 GB card gives it half), and 6 or less gives it the whole card. See [Scaling and tuning](/guides/scaling/). |
| `MINERU_LLM_AIDED_*` | off | MinerU's optional LLM-aided heading levels and cross-page table merge, for PDFs. Either switch needs `MINERU_LLM_AIDED_BASE_URL`, `MINERU_LLM_AIDED_MODEL` and `MINERU_LLM_AIDED_API_KEY`, and sends heading or table text to that API. Leave a switch at `false` rather than empty: MinerU rejects an empty value, and every job fails. |

Upgrading an endpoint created from a 1.x release? Delete `MINERU_VL_MODEL_NAME`
from its environment: MinerU 4 rejects it alongside a per-job `server_url`.
`MINERU_MODEL_SOURCE` (the image sets its own), `MINERU_WARMUP_BACKEND` and
`MINERU_WARMUP_LANG` (replaced by `MINERU_WARMUP_TIER`) are leftovers to delete
too, along with any RunPod Cached Models entry.
[Upgrading to 2.x](/getting-started/upgrade-to-2/) lists every change.

## What to do after deploy

RunPod gives you an endpoint id such as `abcdef123456`. It accepts the
documented [job input contract](/reference/api/) through the standard
`/run` and `/runsync` endpoints.

1. Follow [Clients](/getting-started/clients/) to submit your first parse.
2. Enable [OpenTelemetry](/guides/observability/) if you need searchable
   logs, per-job traces, GPU metrics, or production alerts. The exporter is
   already in the image and remains off until you set an OTLP endpoint.
3. Review [Scaling and tuning](/guides/scaling/) before raising worker or
   in-worker concurrency.

Before production traffic:

- Keep API keys and bucket credentials in the endpoint environment, scope
  them to the resources this worker needs, and keep them out of job payloads.
- Choose the [input source](/guides/input-formats/#size-limits) and
  [output mode](/guides/output-modes/) for your document sizes. Large outputs
  usually need S3-compatible storage plus a bucket lifecycle policy.
- Align the client timeout with the endpoint execution timeout, then test a
  representative worst-case document.
- Add application-level retries and idempotency if jobs are business-critical;
  the starter client does not retry. Review the worker's
  [cancellation limits](/guides/troubleshooting/#cancellation-and-worker-recycling)
  before promising hard mid-parse cancellation.
- Enable [OpenTelemetry](/guides/observability/) with a production-safe
  cardinality and data-retention policy.
